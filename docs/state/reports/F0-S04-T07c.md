# F0-S04-T07c: diagnóstico da trava do caso `destruir janela` (Windows)

- Data: 2026-10-22 · Implementador: sonnet (diagnóstico) · Nenhum arquivo do produto ou de teste foi mudado.
- Conclusão curta: **não foi possível reproduzir (0 de 12) e as pilhas disponíveis não bastam para provar a causa.** Hipótese forte de defeito do produto (espera sem limite em `Motor::parar`), mas ainda sem prova. Falta uma medição maior e uma pilha nativa.

## 1. Onde trava (os dois logs do CI)
- PR 241, run 39589194369 (`windows-viewport-a`): `faulthandler` aos 380 s mostra **só a thread principal do Python**, parada em `test_s04_viewport.py:383` (`c_destruir`, linha `shiboken6.delete(w) if i % 2 else w.deleteLater()`), chamada de `passo` (l. 439). O log não diz em que volta (0 a 11) estava: o caso não imprime progresso. A linha 383 só é "delete síncrono" nas voltas ímpares; a pilha não mostra a volta.
- PR 250, run 39683579825 (`windows-viewport-b`): thread principal só em `rodar` l. 447 (laço de eventos), sem frame de `c_destruir`. Ou seja, o laço de eventos girava, mas `passo` não avançava ou nunca terminava: coerente com um `delete`/`parar` preso que já passou, ou com um passo que nunca é reagendado.
- `faulthandler` só mostra threads Python. A thread de desenho do C++ (`Motor::laco`) não aparece em nenhum dos dois logs: **não há pilha nativa**.
- Histórico: o LOG já tem uma falha do mesmo caso em 2026-10-19 (PR 188, `windows-viewport-a`). Total: 3 ocorrências em ~3 dias, só no Windows, em PRs sem mudança de viewport.

## 2. Taxa medida (job temporário `windows-t07c`, PR 256 fechado sem mesclar, ramo apagado)
- Run 39844219006, job 120053086013, windows-latest, WARP/d3d11, mesmo ambiente do `caso()` (QT_QPA_PLATFORM=windows, RHI=d3d11, LC_ALL=C, sem DISPLAY), `OBIM_LIMITE=100`, subprocesso novo por volta.
- **Travas: 0 de 12.** Todas com código 0 e "RESULTADO" no stdout, 6,8 a 8,6 s cada (mediana ~7,0 s). O plano de capturar threads do processo travado (PowerShell, aos 65 s) e a pilha do `faulthandler` (aos 80 s) ficou pronto e não foi acionado.
- Leitura honesta: se a taxa real fosse 1 em 8, a chance de ver 0 em 12 é ~20%. **12 voltas não bastam para dizer "não trava".** Também importa que o caso isolado difere do CI real: lá ele roda depois de ~210 testes no mesmo passo, com fixture `viewport` e máquina já carregada.

## 3. Hipótese de causa (a confirmar)
`Motor::parar()` (`nucleo/motor.h`) faz `while (!terminou_) { bombear(); sleep(1 ms); }` **sem limite de tempo**. Chamado por `~Janela` -> `desligar()` quando o Python apaga a janela com a thread de desenho viva (o caso sem `parar()`). Só termina se `laco()` chegar ao fim. A thread de desenho pode ficar presa no D3D/DXGI (soltar swapchain, `Present`) esperando a thread da janela por uma mensagem enviada entre threads; `bombear()` usa `PeekMessageW(..., PM_NOREMOVE | PM_QS_SENDMESSAGE)`, que atende só mensagens enviadas, e não cobre todos os casos de espera cruzada do DXGI. `soltar_superficie` tem limite de 3 s, mas `parar` não tem nenhum: se a thread nunca sair, o processo fica parado até o `faulthandler` (380 s no CI), exatamente o que se vê. O delete síncrono (`shiboken6.delete`, voltas ímpares) mantém o GIL durante o destrutor, mas a thread de desenho não chama Python, então o GIL não explica sozinho.

## 4. Proposta (cartão futuro; nada implementado)
1. **Instrumentar antes de corrigir** (cartão T07d, ramo sem merge): `c_destruir` imprime a volta; no travamento, o subprocesso despeja a pilha nativa de todas as threads (no CI Windows: `cdb`/`procdump` exigem instalar ferramenta, então pedir ok do PO; alternativa sem instalar: `MiniDumpWriteDump` chamado por uma thread vigia dentro do `obimcore` só em modo diagnóstico).
2. **Medir mais**: 100 voltas do caso isolado no Windows (~12 min) e também o caso dentro do pytest completo do `windows-viewport-a`, que é onde ele falha.
3. **Correção provável**, se a pilha confirmar espera em `parar`: dar limite a `parar` (por ex. 5 s), como já existe em `soltar_superficie`; no estouro, marcar a swapchain/QRhi como perdida, deixar a thread para trás sem `join` (vazamento controlado, contador novo `paradas_atrasadas`) e não travar o processo. T3: exige oráculo em subagente separado e revisão Opus em lote.
4. Não aumentar o tempo-limite do teste nem afrouxar o caso (armadilha do cartão).

## 5. Conclusão
Ainda não se pode dizer "defeito do produto" nem "ambiente": 0/12 isolado, 3 falhas em ~210 testes no CI real. O que o código mostra é uma espera sem limite em `parar()`, que transforma qualquer lentidão ou impasse da thread de desenho em processo parado. Isso é um risco do produto mesmo que o gatilho seja o runner. Recomendação: abrir T07d (instrumentar + 100 voltas) antes de mexer em `viewport.cpp`.
