# F0-S04-T07c: diagnóstico da trava do caso `destruir janela` (Windows)

- Data: 2026-10-22 · Implementador: sonnet (diagnóstico) · Nenhum arquivo do produto ou de teste foi mudado (os experimentos rodaram em PRs temporários, fechados sem mesclar: #256 e #258).
- **Conclusão: a causa foi achada.** A thread de desenho trava dentro do próprio Windows, ao destruir a placa de vídeo virtual (WARP, usada no CI e em PCs sem placa compatível). `Motor::parar()` espera essa thread sem limite de tempo e o processo fica parado. Não é lentidão do runner; é um impasse raro (~1%) que o produto não limita.

## 3. Pilha nativa do processo travado (volta 43; resumo)
- Impressões de estágio no `Motor::parar()` (só no ramo temporário): `parar: inicio` apareceu e `terminou_` NÃO. As chamadas anteriores, na mesma volta, imprimiram `inicio, terminou_, join ok`; só a última parou em `inicio`. Logo: `parar` espera `terminou_` e o `laco()` nunca termina.
- Thread principal (0): Python -> destrutor do `QWindowContainer`/`QWidget` -> `~Janela` -> `Motor::parar` -> `SleepEx` (o laço de 1 ms). Fica girando, sem travar o laço de eventos.
- Thread de desenho (10): `laco` -> destrói a `QRhi` (`Qt6Gui!QRhi::~QRhi`) -> `d3d11!CDevice` destruindo o dispositivo -> `d3d10warp!UMDevice::Destroy` -> **`d3d10warp!UMContext::Flush` -> `WaitForSingleObject`** (parada).
- Thread do WARP (5): `d3d10warp!Task_DMA_Start` -> `WaitForSingleObject` (também esperando). As duas esperam uma pela outra dentro do WARP; nenhuma trava de mutex do `Motor` está envolvida. Threads do Python (4): espera de lock normal.
- Pilha Python (faulthandler, 80 s): só `rodar` l. 447 (mesmo quadro do PR 250).

## 4. Causa e o que é do produto
- Gatilho: destruir o dispositivo D3D11 do WARP na thread de desenho com trabalho pendente (janela apagada com a thread viva, sem `parar()`); o impasse é interno do WARP (Flush x tarefa DMA).
- Defeito do produto: `Motor::parar()` (`nucleo/motor.h`) tem laço **sem limite**. `soltar_superficie` e `capturar` têm limite (3 s e 8 s); `parar` não. Qualquer travada da thread de desenho congela o app para sempre. Afeta quem usa WARP (sem placa compatível; há aviso "desenho por software").
- Não é lentidão do runner nem problema do teste; o teste só expõe o caso sem `parar()`.

## 5. Proposta (cartão futuro; nada implementado; T3: oráculo em outro subagente + revisão Opus em lote)
1. Limite em `parar()` (ex.: 5 s). No estouro: marcar a thread como abandonada (sem `join`, vazamento controlado), contador novo `paradas_atrasadas` em `estatisticas()`, nunca congelar o processo. Cuidado: `std::thread` abandonada precisa de `detach` e de o `Motor` continuar vivo (o `shared_ptr` já existe).
2. Reduzir a chance: antes de destruir a `QRhi`, esperar a GPU ficar ociosa (`finish`/`ClearState` + `Flush` na thread de desenho), para o `Flush` final não ter trabalho em voo.
3. Teste: o caso hoje trava em ~1%; para provar a correção, laço de ≥300 voltas no Windows sem nenhuma trava, e o contador `paradas_atrasadas` aparecendo se forçar a espera.
4. Não aumentar o tempo-limite do teste nem afrouxar o caso.
