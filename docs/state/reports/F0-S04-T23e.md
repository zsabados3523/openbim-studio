# F0-S04-T23e: encurtar a montagem do instalador do Windows

## O que foi medido (antes)
Log das rodadas no `main` (job `instalador-windows`, 2026-10-21): 626 s, 668 s e 793 s no total do job. O log só guarda as últimas 45 linhas do `build_installer.sh`, então só há o tempo do script inteiro: 305 s (`env.tgz` 296 MB, instalador 297 MB); a instalação do R1-j levou 26 s.

Reprodução no Linux (amostra de 950 MB do ambiente de runtime, ferramentas equivalentes; o NSIS não roda no Linux, então o LZMA foi medido com `xz` de dicionário 64 MiB):

| Passo | Tempo | Tamanho |
|---|---|---|
| `gzip -9` do ambiente | 109 s | 323,6 MB |
| `gzip -6` | 28 s | 326,8 MB (+1%) |
| `gzip -1` | 11 s | 364 MB (+12%) |
| LZMA 64 MB sobre o `.tgz` já comprimido | 148 s | 320,3 MB (-1%) |

Conclusão: a compressão feita duas vezes explica quase todos os ~282 s (109 + 148 = 257 s no Linux; o Windows é mais lento) e a segunda não reduz o tamanho.

## Mudança
1. `openbim-studio.nsi`: o `env.tgz` entra no instalador sem recompressão (`SetCompress off` só nessa linha); `/SOLID` sai, para que o `SetCompress off` valha por arquivo sem depender do modo sólido (só o CI do Windows confirma; o NSIS não roda no Linux). O resto do pacote (~7 MB) segue em LZMA.
2. `build_installer.sh`: `gzip -9` passa a `gzip -6`; mostra os tempos do `tar|gzip` e do `makensis`.

Ganho esperado: de 148 a 230 s por montagem (a segunda compressão some; o `gzip -6` poupa ~80 s). Bem acima do piso de 60 s do cartão.

## Conteúdo instalado idêntico
O fluxo de bytes do tar não muda com o nível do gzip: o SHA-256 da saída descompactada de `gzip -9`, `-6` e `-1` é igual ao do tar original (`f87cad16...fa02`, teste local com a amostra). O NSIS só guarda o arquivo; o `tar.exe` do Windows extrai os mesmos arquivos.
